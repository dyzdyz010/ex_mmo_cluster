## 3. v2 新合同的独立反例

### 3.1【严重】绑定组仍缺祖链／组间重叠与迁移集合的闭合；“只检查 W”无法执行 R 的承诺

**稿内证据**：`S:98` 定义“实例：home 页 ∪ 覆盖页集”；`:102` 要求“影响写结果的读必须在本分区”；`:106` 的实际准备规则却只处理 `W(op) ⊄ 本分区`。`:104` 的外一圈只写所有权约束，没有写 T1 怎样保持它。

**源码证据**：`VR/world/prefabs.ex:50`—`:72` 通过 `parent_id` 求子树，`owner_cells` 返回整个子树的宏／微格；`VR/world/payloads.ex:211` 明确调用 `Refined.ancestors`；父稿 `P:137` 的读取闭包包含“祖链所在页”。M2a 当前 `VR/world/pages.ex:99`—`:100` 只是把 aid 归 owner home，并未实现一套可直接复用的全部覆盖页集；父稿对此是 M2b 目标，不能混称 M2a 已完成。

**推断／反例**：若“一个实例”仅指一个 occurrence，父节点 home H 与远处子节点页 P 各有自己的绑定组，两组可能不交；在 P 读取祖链或删除父子树仍跨片。若打算根实例组包含整个树，必须明确这一点。两个不同组共享页 Q 时，也不能各自任选基础网格一侧；它们必须传递合并。另有冷页 R 作为活动岛的外圈，虽不在模拟集内，却不能被另一个 T1 仅因“冷”而夺走。

**最小补充**：定义绑定关系的传递闭包及其唯一来源；整个迁移页集也须包含所有绑定成员、仍被依赖的 buffer 和相应写权，不是只把最初缺的几页写进 `voxel_migration.pages`。把裁决所需 R 的准备／所有权验证补入执行规则，并明确冷维护、远程查找和新对象足迹如何失败或取得依赖。既有数据／目录中的组关系用派生计算和现有版本复核维护，不另造可各自修改的第二份组真值。

### 3.2【中】R-merge 的产品身份已正确承认，但资格公式不能代替完整分量准入与进展规则

**证据**：`S:117` 用逐页交集定义 S；`:118` 又要求跨分区电路“分量整体保持冻结”，`:120` 改用潜在连通图。现 `VR/circuit.ex:29`—`:31` 按开关与温度决定当前导通；`VR/world/thermal.ex:329`—`:344` 沿实际导体迭代发现。

**推断／反例**：电路一半在 A、一半在 B，逐页交集会把 A 半保留在 S，却没有体现“整分量暂不授予”；若岛只从这个已裁剪 S 求出，远端需求又可能从发现／迁移驱动中消失。两侧都等待对方迁移、控制面只看已激活岛时，冻结可永久维持，不能只靠“提前触发”保证最终合并。

**要求**：区分期望资格／发现闭包与已接纳可执行资格，按完整电路或不可分割过程授予资格；写出发现未完成、并发合并、超预算时的等待／拒绝与唤醒。发现批次大小、触发余量和性能值可留 S0/S3，但“谁持续推动、什么时候成功或明确失败”必须是方向合同。Folia 官方原句“a ticking region cannot expand the chunk positions it owns as it ticks”支持在执行前维护所有权，并不替本项目决定物理冻结或无限等待。[Folia Region Logic](https://docs.papermc.io/folia/reference/region-logic/)

### 3.3【严重】共享锁解决了写／翻转竞态，但 prepared 的合法性、重叠迁移与节点换化身尚未进入决定守卫

**证据**：`S:166` 对 owner 行 `FOR SHARE` 后校验 `partition = 我`；`:174` 迁移行保存 `src_incarnation`；`:178` 的 prepared 更新只比较迁移行自己的 `src_incarnation`；`:179` 的 committed 更新只明确检查 state、源前缀和目录摘要，没有校验**当前分区化身、当前 owner 仍为预期源、该页当前迁移标识**。`:181` 的源重启只扫描 prepared，不说明 planned 期间已冻结／已发持久写的恢复。

**推断／反例一**：M1、M2 都基于 A 的页 p 准备，分别去 B、C。控制面依次提交 M1 和 M2；“唯一决定者”仅使 SQL 串行。若按稿列出的条件，M2 仍是 prepared，旧 A 前缀也够大，便可把已归 B 且已有新提交的 p 改给 C，并引用旧 A 基线。必须有逐页排他的迁移关联或等价条件更新，才能排除此执行。

**推断／反例二**：A 的 prepared(C) 已持久，随后节点故障重派并 bump 化身。控制面不能仅看迁移记录里的旧 src_incarnation 相等就继续旧决定；新源必须明确继承该冻结决定，或让旧准备失效后重新准备。冻结后但 prepared 应答未知、planned→prepared 与恢复同时发生，也须按当前持久状态处理，不能因只查到 planned 就允许不受约束地写 C+1。

**要求**：补上迁移状态转移的完整守卫、受影响行数判定、目标激活与恢复驱动，明确源／目标换化身和重复请求；同一决定锁住这些条件直到翻转。`DS/body_store.ex:45`—`:46` 的原子 `WHERE cid = $1 AND owner_epoch = $2` 正是“检查实际权利并写”的参照。PostgreSQL 原句：“A shared lock blocks other transactions from performing UPDATE, DELETE, SELECT FOR UPDATE or SELECT FOR NO KEY UPDATE on these rows”。该原语有效，但不会替应用判断“这个 prepared 仍合法”。[PostgreSQL Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS)

**【中】同一节的 GC 授权还自相矛盾。** `S:166` 把残留清理等所有持久写统一要求 owner 是我，`S:195(c)` 又要求源删除“不再拥有且无人引用”的旧页行。后者本来就不是当前 owner，不能过前一个谓词。应把“写权威数据”与“清理本流已退休历史”的授权区分，且检查无引用与删除在同一冲突边界；不是给 GC 留无条件后门。索引、锁顺序及死锁重试策略可到 S2 细化。

### 3.4【严重】导入只设置 `next_seq` 并标脏，没有把新基线纳入目标流的已提交顺序与切点

**证据**：`S:191` 用本流可见版本与导入基线取 max；`:194` 要求导入后首切点写本流并清 base；`:258` 只提升 `next_seq`，没有提高已提交 `seq` 或定义导入提交。当前 `VR/world/page_cut.ex:188`—`:200` 只在 `state.seq > published` 开切点；`DS/voxel/page_store.ex:67`—`:68` 拒绝不前进的发布。当前页行按段／chunk 选 `max(cut_seq) <= P`（`:111`—`:114`），不是每页一条完整记录。

**推断／反例**：B 已发布 P=100，导入 A 的 C=900，next_seq 改为 1001，但没有普通玩家提交。B 把页标脏后请求首切点，现有 owner 仍以 seq=100 判已覆盖而不开；若强写 cut=100，则新版本数字还小于导入的 900，违反可见性 max 的单调前提。B 随即再导出或角色离线，就无法满足“已发布本流基线再翻转”的约束。不能依靠未来恰好来一笔编辑使迁移收口。

**最小补充**：明确导入成为目标流一项已提交事实的序号、后缀／前驱、角色与全局行，以及没有玩家新输入时如何完成首切点；或者给出不依赖本流伪造旧切点的明确导入状态合同。每段基线应是“源在 C 的最新可见段版本”，不是要求该段恰有 cut=C。清 base 必须发生在全套段已可见之后；保留空段／删除，不以新流缺行冒充 baseline。首切点重写还是长期引用是性能取舍，可晚定，但至少一条可恢复路径须先成立。

### 3.5【严重】跨源屏障仍可能跳过目标已提交事务；CollisionStream 收到封口也不等于 Scene 已消费源尾部

**证据**：`S:201`—`:204` 规定源封口后，目标回复源基线 C、目标“当前 seq P_t”，随后只发 `seq > P_t`。`S:182` 又要求目标接续订阅后才接纳意图，而 `S:203` 的续订前置是迁移“已激活”，两个激活阶段没有区分。当前 `VR/canonical_feed.ex:32`—`:34` 是真正发送 delta 的进程；`VR/collision_stream.ex:91`—`:94` 发事件后仍将其保留 pending。`SS/movement/collision_updates.ex:80`—`:83`、`:107`—`:109` 的移交快照还包含未消费队列。

**推断／反例**：目标已经接纳迁入页并提交 D，某个迟到／重试的订阅才到达。用源 C 作基线、把前驱直接设为当前 P_t≥D，再只发 P_t 之后，就跳过 D。即使首个激活打算等待全部订阅，也必须定义“已导入可订阅”和“允许写”两个时点，以及目标崩溃重启、部分订阅已接上／部分未接上的恢复；不能只在一句正常路径里排序。

**另一个空档（推断）**：源只冻结迁出岛，其他岛仍提交，canonical 对订阅者仍发送空投影（`VR/world/observation.ex:394`—`:409`）。封口 C 必须恰好排在本流 C 与后继之间；若等后台发布 C 的应答后才插 marker，C+1 已经可能在 feed 中。即便 stream 收到 marker，Scene 还有未安装的尾部，不能在控制消息到达时越过其队列重置前驱。

**最小补充**：选定目标导入后的精确续订切点，保证 C 到该切点的相关变化被重放或在订阅全部建立前禁止发生；续订重复／超时必须返回相同可证明的衔接结果。封口与切换事件都进入既有 canonical FIFO，在 Scene 消费边界完成，而非旁路改水位；对 abort 恢复、已开始但未完成的窗口请求、旧源 monitor 与 Replica 有明确结果。`baseline_transaction_seq` 的流送路径当前为 nil（`SS/movement/collision_updates.ex:47`—`:48`、`:102`—`:103`），因此不能一概要求重建该字段；非流送路径有共同基线守卫（`:171`—`:172`），可明确限用／失败，不能默默混用。

### 3.6【严重】`next_seq`、附件 id、块分配是不同基数的分配问题；目前的统一改法会漏掉一笔多 id

**证据**：`S:247` 要把 45 处统一成 `state.next_seq`，并注明“含……附件 id”；`:251` 又承诺 K=1 号连续、同输入 id／回执相等。实际 `VR/world/prefabs.ex:463`—`:470` 为每个附件组依次推进 `attachment_serial`；`:495` 整个 prefab 只推进一次提交 seq。`VR/world/parcel.ex:107` 生成 `{seq,n}` 的实例 id，`:108`—`:110` 则为多个 aid 分配 `base+n`。

**推断／反例**：一笔 prefab 有两个附件组，把它们都替换成同一个 next_seq 会撞 aid；保留 `serial+1` 又可能越过本流块尾进入另一分片号段。若附件 id 与提交号共同消耗同一块，K=1 的提交号也未必仍连续，原 id 逐项相等未必是合法验收目标。这里不能以搜索命中数决定机械替换。

**要求**：先明确“一笔一个提交号”与“一笔零到多个附件身份号”的合法分配合同，涵盖事务失败、块尾不够、批量安装、重启废弃尾块；选择能保留线格式的最小实现，而非提前承诺所有数值都不变。前驱只由权威提交序列／明确投影派生；`S:248`“本订阅者收到的上一笔”应澄清是被该流接纳／发出的前驱，不要为每个消费者再维护独立可写的正确性水位（`AGENTS.md:56`）。

**【中】新块必大于所有旧块也不是任意 PG sequence 配置的性质。** v2 `S:259` 的证明需要约束块预留方式、数据库 session 缓存和目标最小值。官方文档原句：“the values might be generated out of sequence when all the sessions are considered.”；同页说明 CACHE>1 时各连接会持有先前预留的值。[PostgreSQL CREATE SEQUENCE](https://www.postgresql.org/docs/current/sql-createsequence.html#SQL-CREATESEQUENCE-NOTES) 不必本轮定块大小，但须写成明确号源保证并给保证它的官方机制，不能只引用“允许空号”。

### 3.7【中】令牌、热账与冻结时间新增了跨 owner 效果；幂等键与简单时间平移还缺持续维护

**证据**：`S:137` 称令牌归还“只会暂时多计”；`:138` 用同一迁移 id 对消导出／导入；`:182`、`:216` 在激活时把冻结时长加到时间锚点。`WS/movement/projectile.ex:30` 实际年龄由 `(now - s.t0_us)` 推出，`:31` 仍要求候选 actor 与原 `source.identity`、life_generation 相等；`VR/world/projectiles.ex:85`—`:86` 已有“先持久冻结交付对象”的真实可靠性入口。

**推断／反例**：拟态在别片消散并提交后，发送归还前进程崩溃；只有接收端去重不能恢复丢失消息，令牌可永久占用，绝非只短暂多计。源已记导出而迁移 abort，或目标重复激活记两次导入，也不会因为 id 相同就自动对消。目标第一次平移 t0 后持久化，重启再按原冻结起点加一遍，会延长寿命；abort 只“解冻”而不处理锚点，又会补算暂停时间。

**最小补充**：令牌归还应有唯一 owner 持续维护的待交付事实和明确确认／退休规则，复用现有持久交付实践，不泛建消息框架；热账与时间调整应由持久迁移决定和既有提交状态推导或一次接纳，明确 abort／重复激活。把“源封身体、世界账翻转、Session 移交、目标 BodyStore.claim”中间失败的恢复驱动写清，`S:211`“目标重启装入”不能替代 Session／Player 的恢复。令牌释放滞后和登录源不可用的可见行为交用户决定。

改投射物候选到当前分区是必要接线，但仅改 `scene_id` 不够：施法者 TC 后旧 source.identity 仍不匹配新角色，当前 sample 分支 `WS/movement/projectile.ex:31`—`:39` 会没有 actor 而得不到 hits。旧生命／新会话分别怎样影响已发射对象必须明确，不能无意扩大或缩小攻击有效期。该产品合同在 S1a/S3 对应改动前确定，具体投递实现可随步骤细化。

### 3.8【严重】Scene 收窄不能直接复用现有“单包围盒”边界；协议 41 字节不变仍须给出可表达方案

**证据**：`S:150` 要把任意页集收窄为可行走范围，`:151` 据此证明窗口始终单源；`S:250` 承诺客户端不改。`apps/mmo_contracts/lib/mmo_contracts/voxel/codec.ex:23`—`:24`、`:40`—`:41` 只编码 `travel_min_m`、`travel_max_exclusive_m`。客户端 `客/Movement/MmoPrediction.cpp:146`—`:151` 直接构造一个 `VmAabb` 并 `vm_constrain_travel`。服务端真正停止移动的是 `SS/movement/player.ex:1663`—`:1666` 的 `domain_at(...).travel`；`:1706`—`:1723` 的 authority 越界逻辑主要是找邻居发移交请求，没有邻居时不自动形成新墙。流送 travel 还由 `:2072`—`:2087` 按窗口盒派生。

**推断／反例**：T1 让 A 拥有 L 形或带洞页集。对其收窄的结果也可能非凸；取包围盒会把缺口／他区包含进可行走范围，取一个内接盒则会阻断实际合法的另一条臂。只改 server authority 而客户端继续用旧 travel，会发生预测越界和回拉，不能证明“协议与客户端都不改”。动态缩小范围若把当前预测位置排除，客户端 `:139`—`:141` 甚至会结束为 `UnsupportedRange`。

**最小补充**：明确采用何种协议 41 可表达的每玩家有效域、怎样随窗口／fence 同步切换并保留当前合法位置，或者承认客户端／协议需要相应变化；不能先假定任意页集等于一个 AABB。已有已安装／待装窗口还须被迁移计划保留到退休，而不只是对“当前位置新算的窗口”做收窄。此问题从 S2 的 T1 已存在，不属于仅 K≥3 才出现的 S4 邻居数问题。

### 3.9【严重】S2–S4 的“区域请求只含本分区片段”提前使用了尚未定义的片段协议

**证据**：`S:269` 要求区域请求“只含本分区页的片段”，`:270` 才把完整／增量／删除表示、片段缓存守卫列为 S5 协议 42 工作。现 `VR/world/payloads.ex:243`—`:245` 以整区载荷替换详情，`客/Voxel/Net/VoxelRegionFetcher.cpp:66`—`:81` 仍按一份 header seq 重放区域事务；没有片段级缺失状态可直接使用。

**推断／反例**：L3 区域包含 A、B 页，S2 只让 A 返回自己片段。若包装成普通完整区域，B 的编辑真值要么被 baseline／空气替代，要么没有可表达的“未知”；若只发增量，首次访问还没有所谓“最近一次完整取得的内容”。Test-only 标签允许暂不验远景，不允许把不完整来源伪装为已确认完整区域，也不能保证它不会影响全局 AppliedSeq 与意图观察。

**最小修订**：在 S2 实跑范围中明确采用可执行的隔离办法（例如限定远景能力／请求范围，或先补必要片段接纳），不要同时承诺旧 codec 不改和新片段请求已可用。可以留远景最终一致与全级缓存工程到 S5；近景证据必须免受已知远景错误污染，正常组合根与 Test-only 参数边界保持唯一。

## 4. “仍未闭合”九点的前置等级

以下对应 `S:322`—`:330`；这里区分批准方向需要的合同与后续测量／实现，不要求把全部工作提前完成。

1. **【严重】§10.1，锁覆盖：方向批准前补状态守卫与 GC 授权差异。** 依据 `S:166` 与 `:195` 的相反谓词、3.3 的重叠迁移反例。具体 SQL／索引、固定锁顺序、成本和更少锁的优化可留 S2；不用现在研究第二套算法。
2. **【中】§10.2，冻结成本：合同前明确允许阻塞的范围和失败出口，接受数值留 S2/S3。** `VR/world/page_cut.ex:180` 是整流合法边界；没有证据强制先做“只冻岛”切点，允许先实测现有方案。D3 接受之前不可宣称停顿已可接受。
3. **【严重】§10.3，首切点／长期基线：先解决无新编辑也能导入、再导出和恢复的语义，见 3.4。** 全量重写是否值得优化可到 S3；不能把安全性与写放大一起留成未决问题。
4. **【严重】§10.4，订阅：跨源不丢尾部、目标激活边界、失败／重取语义必须先闭合，见 3.5。** Replica 非流送模式可明确不支持迁移或显式拒绝，但须在 S2/S3 对应入口前落地。`serve_item` 旧头与远景片段的完整工程可留 S5，S2 临时隔离方式先写清。
5. **【中】§10.5，令牌与投射物：产品行为在相关实现前决定。** “只暂时多计”须改为有持久归还保证或显式不可用语义；source 身份／生命验证不能意外改变。不能以新令牌方案未经确认就标 S1a“无行为变化”（`S:279`）。
6. **【严重】§10.6，45 处替换：提交号与多 id 的契约批准前定，逐调用点改造留 S1b。** `VR/world/prefabs.ex:463` 与 `parcel.ex:109` 已给非一对一反例；不要求列出机械的 45 行审批清单。
7. **【严重】§10.7，D7：先明确保护策略与不可默许的数据变化，再批准推荐路线。** 有界化具体高度须用户明确接受且有依据；如果先保留该阶段旧保护机制，应相应限定多分区范围，不能把它写成已经闭合的页绑定方案。详见 5.5。
8. **【中】§10.8，连锁合并：批准前写排他性与活性承诺，预算参数和性能留 S3。** 对同一页重叠 prepared 如何处理属于 3.3 的正确性，不能等负载均衡阶段再补；无界岛的产品容量继续保持明确未验收。
9. **【轻】§10.9，额外外部先例：不阻断。** Folia 与 PG 一手依据足以支持采用其明确适用的局部机制；其他成熟体素系统的持久跨进程岛迁移和 SpatialOS 原警示本轮未核实，不引用为正确性证明，不必为找相似案例无限扩检。

## 5. 决策点与遗漏的产品语义

### 5.1【中】D2 推荐可保留，但跨分区重登的不可用性需要用户接受

`S:310` 推荐角色账跟随角色，有利于普通扣料本地提交，`VR/world/production.ex:60`—`:65` 支持这一 owner 组合。`S:212` 规定源不可用时跨分区登录失败，是新增且真实的可用性边界：存储仍可达也不能自动改在别处出生。需说明源故障重派后如何完成 TC、超时如何提示。未来跨角色转账列非目标即可，删去 1.6 的排他实现断言。

### 5.2【中】D3 是合理的明确取舍，但备选“无墙、两边都停”也不能免除进入边界

`S:311` 已把临时墙和停步交给用户，优于 v1。只是暂停物理不等于玩家可以进入尚未导入的窗口；两种选项都要满足 3.8 的可行走域、窗口和来源约束。需决定等待期间编辑是显式拒绝还是排队、控制面长时间不可用是否断开／保持停步，以及相同动作因部署与合并延迟被拒的可见理由。触发余量可以测后定。

### 5.3【轻】D5 片段级最终一致合理，不能据此改变近景完整性

`S:313` 的协议 42、按 L0 页片段、最终一致和分发前置可以保留；`VR/world/canopy.ex:30`—`:31` 支持 L5 核心祖格归一个 L0 页。首次未知片段、ring 和缓存不具完整性时如何呈现须在 S5 接纳合同里说明。S2–S4 仅验证近景的限制须依 3.9 可执行，而非提前发未定义格式。

### 5.4【中】D6 块分配仍是可选的最小格式改动，承诺应收窄

`S:314` 推荐可以保留，但应表述为“近景提交号字段布局可保持；身份分配、内部顺序及移动域接线另需闭合”，不能把“客户端不改”作为未证前提。新块预留的官方条件、多个附件 id、导入提交点见 3.4、3.6。K=1 等价验收应比较批准语义；若选择改变附件号与提交号的对应关系，不能强求旧的逐数字相等同时又宣称统一号池。

### 5.5【严重】D7-B 的高度转换无独立依据，D7-A 的控制面备选也不是原方案的零成本替换

**证据**：`S:315` 推荐按“该列现有内容 Y 范围外扩若干页”转换；`AGENTS.md:55` 要求实质技术决策有一手依据，原创决策须事先说明理由、风险、不变量和验证。`VR/protection.ex:6` 的原合同不限 Y，`VR/world/claims.ex:64`—`:67` 还按面积、数量、重叠和他人占用判定，不含高度／体积上限。

**推断**：“现有内容”若包含生成地形，可能没有可用有限上下界；若只含编辑对象，又会撤掉保护区内未建空地、高空、地下未来建造权。单纯“列出差异”不是保护存量语义。把保护区永久绑定还会让其覆盖页上的其他绑定组传递合并，影响分区容量。新的高度／体积、认领交互、配额和旧区域迁移都需要产品决定与证据，不能由实现任选“若干页”。

D7-A 若把权限保留为独立全局业务事实、全部体素 page／handoff 仍按 XYZ，可作为待审的替代方向；但不得重新引入 XZ 页 owner。其“各分区应用并复核后成功”没有规定并发创建／释放／占用修改时的原子决定，且是本稿“跨界只迁移”的显式例外。应先选接受哪种成本与语义，再细化，不把两个未闭合选项合称 D7 已解决。

### 5.6【中】D8 顺序可以保留，但决定门槛应早于 S0；P5 后置只意味着累积驻留尚未收口

`S:278` 已在 S0 实施 M2b、P6 和潜在图，`S:289` 却把 D8 留 S2 前，先实施后确认不合理。D8 与 P6 相关产品规则须在 S0 相应改动前明确；预留具体故障／性能阈值在首次实测后定没有问题。内存口径按 1.7 修正即可，不要求把所有 P5 工作前插。

### 5.7【中】D10 按分区计 ticket 可选择，但合并／拆分会改变正在运行的过程，不能只写“总容量随分区数增长”

**证据**：`S:318` 推荐每分区计；父稿 Q1 `P:256` 要求超限按最早者冻结并记日志，`P:212` 要求预算冻结不因重启复活。**推断／反例**：A、B 各在上限内，合并后一个分区立即超限；若用同一上限，就要冻结原本合法推进的过程。拆分是否重获资格、迁入时哪些 ticket 被冻、冻结排序如何跨流比较，都会直接改变水流、燃烧和投射物。该决定不应等到 S3，P6 在 S0 已依赖预算合同。

还应显式交用户的变化有三项：`S:120` 潜在连通图限制合法布线；`S:137` 令牌归还滞后导致消散后暂不能再施法；`S:317` 新放置／维护足迹碰到另一活动岛时拒绝，结果依赖当时岛分布。它们可以合并到现有 D3／D9／D10，不必新增一套决策表，但不能藏在“实现细化／无行为变化”里。

## 6. 结论：批准前最少六项修订

### 6.1【严重】v2 暂不原样批准；以下六项是合同修订，不要求提前完成全部实现或性能验收

1. **【严重】闭合空间依赖与产品前提。** 明确绑定组的祖链／重叠传递、T1/T2 集合与 buffer、R 的实际准备规则、期望／已接纳资格及合并活性；潜在连通图、D7、D9、D10 和令牌滞后的产品变化列为真实待决。证据：`S:98`—`:120`、`:315`—`:318`，本报告 3.1—3.2、5.5—5.7。
2. **【严重】补迁移状态的完整守卫与恢复驱动。** 同页重叠迁移、当前 src／dst 化身、owner 与 migration 关联、prepared 应答未知、节点重派、Session／BodyStore 中间失败必须有唯一结果；区分权威写和退休历史 GC 的授权。证据：`S:166`—`:184`、`:211`，本报告 3.3、3.7。
3. **【严重】补导入的已提交事实与一次生效。** 无普通编辑也能形成目标流基线、首切点与再迁出；页段、角色、热账、时间锚点、令牌归还均可按持久决定恢复，不靠下一笔操作、不因 abort／重复激活改变余额或时间。证据：`S:137`—`:138`、`:191`—`:196`、`:216`，本报告 3.4、3.7。
4. **【严重】重写跨源订阅与可行走域的接线证明。** 不得跳过目标导入后已提交尾部；封口与切换在 Scene FIFO 消费边界生效。为任意页集给出协议 41 可表达的 travel 方案，或明确客户端／协议改动；S2 前远景隔离须可执行。证据：`S:150`、`:201`—`:205`、`:269`，本报告 3.5、3.8、3.9。
5. **【严重】分清一笔一个 seq 与一笔多个 id。** 说明块预留保证、块尾、附件批量分配、重启与导入取号；纠正对 F5.3 的误读，取消未证的 K=1 数字完全相等承诺，前驱从权威流派生。证据：`S:247`—`:262`、`VR/world/prefabs.ex:463`、`VR/world/parcel.ex:109`，本报告 1.5、3.6。
6. **【中】修正验收前提与决策时机。** 纠正“按需装页但整个分区常驻”、双写判定器和远景错误定位；D8／P6／D10 等在首次依赖前定案。新增反例只围绕上述接缝，预装优化、锁成本、具体阈值与额外外部案例留各步骤，不再扩成全套流程门禁。证据：`S:278`—`:303`，本报告 1.4、1.7—1.8、第 4 节。

### 总评（8 行）

【轻】v2 正确吸收了共享锁、持久决定、显式基线、前驱与真实积压计数等主要方向。
【严重】“有 prepared 记录”还缺当前化身、owner 与重叠迁移的决定守卫。
【严重】导入没有普通新提交时怎样形成目标切点、重复激活怎样只生效一次，仍未闭合。
【严重】目标当前 seq 不是源基线的无损续订点，封口必须贯穿实际消费 FIFO。
【严重】现有单 AABB 不能直接表达任意页集收窄；多附件 id 也不能等于同一 next_seq。
【中】F 的有限块内 max+1 被误读；预装停顿保证、远景定位与整区驻留说法需纠正。
【严重】保护区有界化和其他玩法变化需真实产品决定，不能由架构名词替用户批准。
【严重】先修上述六项再批准 v2，优化与数值验收可后置；本轮仅静态交叉评审，未执行运行验证。
