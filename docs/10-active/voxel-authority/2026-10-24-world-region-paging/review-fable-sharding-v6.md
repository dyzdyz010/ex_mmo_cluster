## 1. 零停顿是否成立（§1 目标 8 对照 U1–U9）

**1.1【严重】U2 / U3：所有权前置在“两分区玩家互相接近但未到合并距离”时会争抢同一冷页，正常包络内即产生 `prefetch_late`。**
S:163 预取集 = `r_own + d_pre` 内不归己的冷页立即 T1；S:165 合并只在两岛“岛 ∪ 外圈”距离 < d_merge 时触发；S:254 再迁要求前一迁移 `done`，而 `done` 要等源“首个覆盖 H 的切点”发布后的释放（S:248），常规切点间隔 30 s（`page_cut.ex:29`）。
反例（无故障、速度在包络内）：A ∈ P1、B ∈ P2 沿同一条线平行行走，间距 D 满足 2·r_own + d_merge ≤ D < 2·(r_own + d_pre)（稿内未排除这一区间，d_pre、d_merge 都留 S2/S3 实测）。二者之间的冷页 p 同时落在两个预取集：P1 先 T1 得到 p；P2 看到 p“不归己且不在任何岛外圈”→ 计划 T1 p → P1，但 `migration` 未清（P1 的 T1 要等 ≤ 30 s 的切点 + 释放）→ 阻塞；释放后 P2 拿到，P1 又因 p 仍在其预取集再 T1 回来。p 在两分区间来回，每次至少一个切点周期。B 走到 p 时 p 未归 P2 → D13 ② 下窗口不能发 → “慢准备停步”（S:170 自认）；D13 ① 下 B 在 p 上的编辑按 D9 先 T1（S:151）→ 等待可达 30 s 量级，等价于编辑被拒。
稿内没有冷页争抢的仲裁规则（谁近谁拿 / 已持有者保留 / 争抢即视为“将相接”提前合并），也没有把 T1 的 `done` 从“等常规切点”解耦（prepared 提交后立即排一个切点，或释放不等切点）。这是正常路径的停顿来源，不是事故路径。

**1.2【严重】U1：源在 prepared 之后的本流写一旦触及成员就被 §4.1 判为僵尸自停，正常路径可复现。**
S:231 权威写（含“页段写回”）要求成员 owner 行 `migration` 为空或为“以本分区为 dst 且已导入”的迁移；S:233 加锁后校验失败 = 僵尸 → 停止进程；S:234 收尾写回授权只在 `state = 'committed'`。
反例一（切点）：源在 H 之前已 `schedule` 了 30 s 定时器（`page_cut.ex:72-83`），定时器在 prepared 之后、目标翻转之前到期 → `maybe_open` 取 `units = page_dirty`（`page_cut.ex:188-196`），其中含 H 前编辑过的成员页 → 写回进程以 §4.1 写成员段行 → `migration = m`、迁移仍是 prepared → 既不满足权威写也不满足收尾写回 → `:stale_owner` → 健康的源自停、其全部岛的意图失败（S:325）。
反例二（步进）：停写只说“停止接纳触及成员的意图与步进”（S:245），但热工作集（接触图、视线缓存）是整流重建的（`claims.ex:100` 注释与 `Thermal.rebuild_work`），稿内没有要求停写时把成员页从热 / 液体 / 投射物域中剔除并重建工作集；一次本应只走非成员的热提交若写到外圈成员页（岛 ∪ 外圈都是成员，S:150）同样触发反例一。
最小修法：收尾写回授权放宽为 `state ∈ {prepared, committed} ∧ released_seq IS NULL`（两态内容都冻结在 H），并写明停写时成员页从切点单元集与所有步进域中剔除；僵尸判定只对非成员键成立。

**1.3【中】U3：d_merge 以常数形式出现，但“整岛预拷贝 p99”随较小岛的页数线性增长。**
S:165-166：预拷贝整个较小岛，d_merge ≥ 2·v_max·(整岛预拷贝 p99 + 交接 p99) + 一页。岛规模无上界（S:221、D4）。固定 d_merge 对大岛必然迟到；若按最大岛取 d_merge，则小岛合并提前到数百米外。需写成 d_merge(页数) 或“预拷贝在限速带宽下的完成时刻”触发（见 §5）。用户前提“资源占用平滑、无不可控尖峰”也未被整岛预拷贝满足（见 4.3）。

**1.4【中】U1 / U6：合并伴随的 M4a Scene 移交仍带可见中断，稿内归入 §10 而不是目标 8 的计量。**
随 T2 迁移的玩家按 M4a 移交（S:307）；现行移交 `begin_body_detach` 先 `cancel_cast`（`player.ex:1040`），sealed 期间丢输入（`:610`）。目标 8 只计“停步区间与编辑拒绝数”，施法被取消、在飞投射物失去 actor 后不再命中（`projectile.ex:38-39`）都不在计量项内。两群玩家相距约 2·r_own + d_merge（≥ 数百米）时就合并，合并频率远高于今日跨 Scene 移交；每次合并取消一次施法是正常路径的可见中断。

**1.5【中】U6：请求转发的顺序保证不覆盖 T2 下请求方自身换进程的情形**（详见 §3.1）。

**1.6【轻】U5：认领 pending 期间矩形内他人编辑“挂起至决定”是正常路径的编辑延迟，决定时长 = 各分区在提交边界投票 + 控制面 + 超时（S:348-353，超时值未定）。**计入 E 记录 ② 即可，但通过条件（S:421）只要求“拒绝数增量 0”，未对挂起时长设上限。

**1.7【轻】其余 U 项**：U4 对投射物成立（Scene 按墙钟取 age，`projectile.ex:29`，`flight_segments` 扫过缺口段）；U7 传送不计入；U8 分类清楚；U9 代价已列。U1 的“停写等合法提交边界”本身不是玩家停顿（意图照常排队），但等待时长取决于源回合长度（M2a p99 384 ms），进入 d_pre / d_merge 的 p99 即可。

## 2. 交接合同与持久化（§4.1–4.4、§4.7）

**2.1【严重】源化身 bump 后收尾写回永远不被授权 → 迁移永不 `done` → 再迁门槛永久卡死。**
S:234 第三种授权要求 `src = 我 ∧ src_incarnation = 我 ∧ state = 'committed'`；S:251 源 bump 时 prepared 不中止，“新化身恢复时…committed 的执行收尾写回与释放”。迁移行的 `src_incarnation` 是停写时写入的旧化身（S:239、245），新化身 ≠ 旧化身 → 收尾写回被拒。时序：源 prepared(H) → 目标翻转 committed → 源节点故障转移（bump）→ 新化身尝试收尾写回 → 守卫失败 → `released_seq` 永不落库 → `migration = m` 永不清（S:248、254）→ 成员永不可再迁。后果：玩家折返或 1.1 的争抢场景中该页 T1 永久失败；D13 ② 下窗口永远发不出（走不动），① 下该页编辑永远等待。
修法：bump 事务同时把该源 prepared / committed 行的 `src_incarnation` 改为新化身（或第三种授权只要求“src 分区行当前化身 = 我”），并在 §8 故障矩阵“收尾写回前源崩溃”里把“新化身能完成释放”写成断言。

**2.2【中】目标化身 bump 与翻转守卫自相矛盾。**
S:247 翻转要求“目标分区行 `incarnation = dst_incarnation ∧ running`”；S:252 目标 bump 后“新化身…经基线链重装后翻转”。`dst_incarnation` 是计划时写入的旧值，新化身翻转必失败，直到 T_abort 中止 → 源解冻、锚点后移（S:268，在途过程可见暂停）。与 2.1 同一修法。

**2.3【中】“目标翻转不校验源存活”对双写安全，但对活性不安全：源活着却收不到翻转通知时，队列与冻结无出口。**
双写层面成立：占用列自 prepared 封住源（S:235），目标只在 prepared 之后翻转，源对成员的任何 PG 写都在 §4.1 被拒。但 S:247 “提交后…通知源”是一条进程消息；源只在“结果不明”时读迁移行（S:255），正常运行的源并不“不明”。通知丢失（跨节点、netsplit 后恢复）→ 源继续冻结成员、排队请求直到请求方超时（S:299 把这归入“源崩溃”事故路径，但这里源没崩）。AGENTS §2.1 第 2 条要求时间性不变量自维护：源在 prepared 后应有界限地轮询迁移行，或控制面重发。

**2.4【中】T1 的 `done` 绑在常规切点上，使“T1 ≈ 两笔提交”只对翻转成立、对再迁不成立。**
S:164 “T1 ≈ 一笔源提交 + 一笔目标提交”；S:248 释放要等首个覆盖 H 的切点，常规 30 s（`page_cut.ex:29`）。若 prepared 提交不推进 `state.seq`（S:245 “H = 该边界的 state.seq”未说明 prepared 提交自身是否占一个 seq），且源此后无别的提交，`maybe_open` 因 `covered?` 为真不开切点（`page_cut.ex:188`）→ 永不释放。需写明：prepared 提交是一笔占 seq 的日志条目（H 即其 seq），且 prepared 后立即 `schedule` 一个短延迟切点（或冷页 T1 的释放不等切点：成员无脏页时收尾写回为空）。

**2.5【中】渐进删除与链引用：现行 `collect` 不查链引用，再迁回源后会删掉被链引用的 H 行。**
`page_store.ex:153-158` 删“被 ≤ 前缀的更新版本取代的段行”。时序：p 由 S→T（T 链 `(S, H1)`，T 未写回 p，链未截断）→ p 再由 T→S（链继承 `(S,H1)`）→ S 写回 p 于 C2 并发布 → `collect` 删除 S 流 p 的 H1 行（被 C2 取代）。此时 T 的链已随再迁交给 S，S 自己写回后应截断——只要“截断”发生在 `collect` 之前。稿 S:280-282 说明了退休须查链引用，但没有规定截断与删除的先后在同一事务内判定；建议写成“删除段行的事务 `FOR SHARE` 该页 owner 行并要求无链项引用该 (流, cut)”。否则 I3 可被违反（目标重装读不到 H 版本，日志已删）。

**2.6【中】“合法提交边界”的定义只覆盖 `thermal_run == nil`，未覆盖停写之后新开的异步步进。**
现 `page_cut.ex:179` 以 `thermal_run == nil` 为边界；停写后源继续为其他岛开热 / 液体 / 投射物步进。稿内须写明成员页在停写后不进入任何步进域、不进入切点单元集（见 1.2）。另：日志整表条目（`log.ex:16-27`）在 H 之后仍会把成员页上的实例记录写进源流日志；源重启回放时这些记录会装回源内存（不是真值，但 S1a 前是第二份副本），需在 S1a 之前明确“按 owner 行过滤装入”。

**2.7【轻】目标翻转时“源对成员尚未截断的继承链”从何读取未写明**（S:247、276）。链是 PG 行（`voxel_owner_base`），翻转事务应在同一事务 `FOR SHARE` 这些行并复制；若链项所引的更早流已被退役并清空（S:315 退役 = 迁走覆盖行后停止），链项 `(Q, H_Q)` 仍可指向 Q 流的已删页表——需要“退役分区的页表与 ≤ 各链项 H_Q 的日志不得删除直到全部引用截断”的规则，稿内无。

**2.8【轻】“封口只发给停写回合已存在的订阅者”**（S:287）。H 之后到达的窗口请求“立即以 H 时快照回”（S:294）但不在封口名单里 → 翻转后它订阅的是源流、永远收不到成员页的更新。D13 ② 下实际不会发生（窗口 ⊆ 本岛），写一句“H 之后对成员的新订阅直接回 `{:redirect, m}`”即可闭合。

**2.9【轻】丢失 ≤ H 内容的其他反例**：未找到。基线 = 已发布页 + 日志 ≤ H 的论证在“日志先于广播”（`edits.ex:198-201`）与“前缀推进与收尾写回同一发布”下成立，前提是 1.2 / 2.1 修正后收尾写回确实会发生。`:stale_owner` 误触除 1.2 外未找到；中止与翻转并发由迁移行 `FOR UPDATE` 定局（S:240）成立。

## 3. 请求转发（§4.5 第 5 条）

**3.1【严重】同一请求方的顺序在 T2 下不成立：请求方（Scene Player）随合并换进程，新 Player 直投目标，旧 Player 的队列尚未转发。**
S:298 的顺序前提是“请求方只在收到携带新分区表版本的回包后改投目标，且改投前等待在途请求全部回复”。但 T2 的请求方是被迁岛上的 Player，它按 M4a 移交为**另一个进程**（`player.ex:1705-1720` `boundary` → `transfer_cut`；新 Player 在目标 Scene 激活），新 Player 的 `authority_ref` 直接是目标分片，不受“等待在途回复”约束。
反例（E3 同格先挖后放）：t0 玩家发 R1（挖，触及成员）→ 源在 [H, 决定] 排队；t1 分区表发布、Scene 移交完成；t2 新 Player 发 R2（放，同格）→ 目标直接执行（目标尚不知 R1 存在）；t3 源收到翻转通知、转发 R1 → 目标执行挖。最终该格为空而不是放置物，且 R2 回“被占用”失败。
同时：R1 到达目标时目标的 `build_sessions` / `tool_sessions` 没有该玩家前值（它们按 `actor.gate` / `actor.player` 键在源内存，`world.ex:1224`、`tools.ex:136`），去重与冷却从零开始；`action_seq` 在新 Player 归零（`player.ex:307`）。
修法：M4a 移交的 seal 必须等旧 Player 发往源的体素请求全部回复（或把它们随 `transfer_cut` 作为 tail 交给新 Player 重投），并把 `client_intent_seq` 水位随角色行迁移；稿内要写成 §4.6 的顺序步骤，不是 §4.5 的一句前提。

**3.2【中】目标在自己翻转之前收到触及成员的请求时的行为未定义。**
3.1 的 t2 若早于翻转：成员页 `partition = src, migration = m`，目标按 §3.1 D9 看到“不归己的页”——它既不是冷页（有在途迁移）也不在他岛规则里。应写明：目标对“dst = 我 且 prepared”的成员请求排队至翻转后、再按与转发队列的合并顺序执行（转发队列先、本地队列后）。

**3.3【中】至多一次 / 恰好一次的边界。**
PG 层恰好一次成立（目标执行即一笔本流提交）。但“队列只清空一次、每条只转发一次”（S:299）与“源转发后崩溃”并不矛盾——风险在**目标收到转发后、执行前崩溃**：请求丢失、请求方超时、`GenServer.reply` 永不发生；而请求方收到的是超时而非失败原因（E3 判定器 5 要求“以超时显式失败”，可接受）。需补：转发消息须带迁移 id 与源队列序号，目标按 (m, n) 去重，否则源在“通知丢失后重读迁移行”（2.3 修法）时可能二次转发。

**3.4【中】直接回包与调用方超时。**
`from` 是 Gate 的 `GenServer.call`（Player 以 `send(authority_ref, {…, from})` 转交，`player.ex:300,309`），跨节点 `GenServer.reply` 可行。调用方超时 = Gate→Player 的 call 超时（稿未列数值）；排队 + 转发 + 目标回合 < 超时才不出现“已执行但调用方已超时”的假失败。这是零停顿的隐含包络，应进 §8 测量“转发增加的确认时延”的通过条件。

**3.5【中】接通转发前必须核实的去重前提**（稿 S:299 自认未核实，本轮已核实，见 §0 表末）：
① 去重键是 (进程键, `client_intent_seq`) 的内存水位，不是持久键；② 冷却 `next_us` 同在内存；③ 客户端不重发。结论：转发本身不会造成二次执行（无重发），但 3.1 的顺序反转与冷却归零是真实的；若将来客户端加重发，必须先把水位随 TC / T2 带到目标。

**3.6【轻】陈旧路由与 `:stale_owner`。**
翻转后源保留转发指针至 `done` 且新表版本已发布（S:295）；`done` 依赖释放（2.1、2.4 的卡死会让指针永久保留，内存泄漏可控但无出口）。`:stale_owner` 只拦 PG 写，和转发互不替代的论证成立。

## 4. 跟随页（§3.6）

**4.1【中】“与 PG 回放同值”的等价论证缺建立时的先后顺序，现文可读成先读 PG 再登记，会丢登记前的提交。**
S:200：“读该页 owner 流的可见版本（PG 已发布页 + owner 日志后缀），并向 owner 登记跟随”。若先读后登记：读到 seq s，登记时 owner 已到 s' > s，(s, s'] 的条目已广播完毕、不会补发 → 跟随页永久落后 s' − s，而“页版本 = 最后改写该页的 seq”只看自己收到的条目，无法察觉。正确顺序只有一种：**先登记**（owner 在同一消息里回当前 seq S_reg 并从此转发），**再读 PG**“已发布页 + 日志 (版本, S_reg]”——因日志先于广播（`edits.ex:198-201`），S_reg 及以前全部在 PG。稿应写死这一顺序；等价论证随之成立（跟随者回放 = 恢复回放，输入集合相同）。

**4.2【中】整表日志条目与“按页筛选”前提。**
稿已列为 S1a 前提（S:204）。补充风险：实例表整表条目（`log.ex:16-27`）无页归属，跟随者若按页筛选会漏掉实例变化、若不筛选会把他分区整张实例表装进内存。等价判定器须把“按页筛选后的回放 == 整笔回放”作为 S1a 的通过条件（S:402 已写），但应明确该判定器要覆盖“同一笔同时改实例表与页内容”的提交。

**4.3【中】内存与流量有界性：有界于活跃区域成立，但不平滑。**
边界带（D13 ①）上界 = 玩家数 × 窗口页数，成立。T2 预拷贝 = 整个较小岛，一次性拷贝，岛规模无上界（D4）；两群接近即触发，是由玩家移动引起的、与岛大小成正比的带宽与内存脉冲，违反用户前提“无不可控尖峰”。应改为限速预拷贝（与 M2a 限速写回同口径），并让 d_merge 包含限速后的完成时间（见 1.3）。§8 的证伪条件（S:412：无玩家不归零、随接缝增长）漏掉：① 退订滞回后残留时长上限；② 每次合并的预拷贝峰值带宽 / 字节是否被限速（应记 p99 与最大瞬时速率）。

**4.4【轻】第二真值判定。**
跟随页“不裁决、不模拟、不写回、不持久、重启即丢”（S:202）满足 SSOT；唯一升格点是导入，其依据是 PG 持久事实（prepared 行 + 日志 ≤ H），跟随状态只是等值的内存副本——4.1 修正后成立。但 D13 ① 下窗口、碰撞由跟随页供数：若 4.1 的竞态存在，客户端的 confirmed 态来自陈旧副本，就违反 AGENTS“缺失 / 陈旧不得冒充真值”。所以 4.1 是 ① 的前置，不是优化。

## 5. 所有权前置与提前合并（§3.3）

**5.1【严重】多群同时接近 / 平行行走：冷页争抢无仲裁（反例见 1.1）。**
d_pre 公式只保证单侧“计划→翻转 p99 内到达”，没有处理两个预取集相交而两岛未到 d_merge 的区间；再迁门槛（S:254）使争抢以切点周期为单位振荡。最小规则建议：预取集相交即视为“将相接”，按提前合并处理（把两岛距离判据从“岛 ∪ 外圈”改为“岛 ∪ 外圈 ∪ 预取带”），或冷页只允许向“玩家更近的分区”迁移且有滞回。

**5.2【中】连锁合并：队列等待不在 d_merge 公式内。**
S:168 “合并中触发的新合并排队”。A←B 合并进行中 C 接近 B（已属 A 的岛）：C 的合并要等 A←B 的整岛预拷贝 + 交接完成，d_merge ≥ 2·v·(预拷贝 + 交接) 没有加排队项；三群一线相向时第三者必迟到。稿 S:469 把“连锁合并的发现预算与参数”留 S3，但这是公式结构问题（需加“队列中前序合并的剩余时间”或允许并行合并不相交的岛对），不是参数问题。

**5.3【中】控制面仍在移动的关键路径上（计划步）。**
d_pre 从“计划”起算（S:163），而需求是分区每拍上报、控制面串行化（S:168）；需求→计划的控制面延迟与吞吐（每拍每分区的需求集可能数十页）不在公式内。应从“页进入预取集的那一拍”起算，并把控制面计划吞吐（页 / s）作为 S2 测量项与包络条件。

**5.4【中】源分区繁忙。**
停写要等源的合法提交边界，源回合受其最大岛的热步进支配（M2a 实测 p99 384 ms、最长 521 ms，S:132）；T1 从 P2（源）拉冷页时，源可能正忙于与该页无关的大岛。d_pre 的 p99 应按“源最长回合”取，而非 T1 自身的轻量提交；稿内未区分。

**5.5【中】r_own / 预取集 / S_want 的关系基本清楚，但 D13 ② 下 r_own 的几何未定。**
窗口 = 已安装 ∪ 已请求 ∪ 待装（S:198），是盒（3×3×3 tile，AGENTS 第 11 条）；r_own “覆盖窗口”应写成“覆盖窗口盒 + 下一次可能请求的窗口盒”（窗口在 travel 盒边缘才请求，新盒偏移一个 tile），否则窗口请求时新盒的外侧一列仍可能未归己。

**5.6【轻】所有权长期随玩家漂移。**
覆盖行随探索单调增长、基础槽与实际归属脱节、分区倾斜（一个分区可能拥有远离其 Scene 基础区的碎片）在 S4 之前只影响 PG 行数与路由表大小，不影响零停顿；可接受，但 §8 应加“覆盖行数与分区页数随时间”的曲线，并写明 S4 拆分是把覆盖行“收回基础槽”的唯一机制。

## 8. D7-A″ 导入补验（§4.10）

**8.1【严重】页带着“已决定认领”的阻挡迁入已应用该决定的分区 → 阻挡永不撤、矩形内他人编辑永久挂起。**
S:349 阻挡按页记、随迁移导入；S:354-355 各分区按版本幂等生效，“仅当 version > 已应用值时应用”，生效时撤阻挡。时序：S 投 yes（p 带阻挡）→ 控制面决定 committed（或 aborted）→ T 已读到决定并生效（已应用 version = v）→ p 从 S 迁入 T（p 仍带 v 的阻挡）→ T 的导入补验只处理“落在 pending 矩形内且不带阻挡”的页（S:350），p 带阻挡且认领已非 pending → 不处理 → p 上的阻挡残留。若决定 aborted：p 上非持有者的写按 S:352 “排队至认领决定”——决定早已发生，队列永不出队（请求方超时）；若 committed：阻挡与保护投影语义重叠，表面无害，但释放（S:357）只移除投影，阻挡仍在 → 释放后 p 仍不可编辑。
修法：导入提交对每个带阻挡的成员页核对认领状态：认领 ≠ pending 或其 version ≤ 本分区已应用值 → 导入事务内撤阻挡并按已应用决定处理挂起请求；恢复回放同样处理。

**8.2【中】源停写期间投票无法给成员页加阻挡，依赖“目标已投 yes 时补验、未投时后投覆盖”，但缺“源投票时成员已 prepared”的显式规则。**
源投票是本流提交，须在成员页上写阻挡；成员自 prepared 起源写不进（S:235）。若投票事务试图写成员页 → 1.2 的僵尸自停反例；若跳过成员页 → 依赖目标补验（S:350 覆盖）。稿应写明“投票跳过 prepared 成员，由目标补验或后投覆盖”，并把这一情形放进判定器反例。

**8.3【中】参与者集合 = 发起时全部 running 分区；pending 期间迁移照常，决定时每个列内页由其当前拥有者复核——成立的前提是“当前拥有者 ∈ 参与者”。**
pending 期间分区起停被互斥（S:347），故拥有者集合不变，成立。但故障转移不受互斥：分区 X 投票前崩溃、新化身恢复后“补做已决定未应用的”（S:356）——若 X 从未投票，控制面等 X 的票直到超时 → aborted；超时值未定，认领请求方等待这一整段。写明超时取值归属即可。

**8.4【轻】挂起请求的队列只在内存，决定前分区崩溃即丢（S:352 自认）。**与 2.3 同类，可接受为事故路径。

## 9. 验收与判定器（§8）

**9.1【中】E1–E3 能证伪“停步 / 拒绝”形态，但漏掉以下停顿形态，记录项 ①–⑦ 不覆盖：**
a. 施法被取消 / 施法条中断（M4a 移交，1.4）；b. 在飞投射物在交接后不再命中（7.2 ⑤）——记录 ⑦ 只记位置序列，不记命中结果；c. 认领第一角丢失；d. 会话级中断：客户端 `End(HistoryUnavailable / ProtocolViolation / IdentityMismatch)`（`MmoPrediction.cpp:114,280,284`、`VoxelM1Client.cpp:621`）与 `cursor_expired` 导致的整窗重取（S:289）——这些比停步更严重，须单列计数并要求为 0；e. 编辑确认时延（记录 ④ 有记录、通过条件无阈值）；f. 认领挂起时长（1.6）。

**9.2【中】“相对 K = 1 基线增量为 0”的判定方法未定义，噪声下不可判。**
停步区间（慢准备）在 K = 1 下本身随机出现；两次运行的总停步时长之差为 0 在统计上不可能。需定义：按路线位置分桶（边界带 ± d 内 vs 其他），断言“边界带内停步事件数 − 基线同位置事件数 = 0”且“所有停步原因码中不出现迁移相关码”；并要求基线运行与 K ≥ 2 运行的位置轨迹逐 tick 对齐（否则“同路线”无法自证）。

**9.3【中】判定器自证只覆盖 E2 的 `merge_late`。**
S:422 只注入翻转延迟复跑 E2。E1 的 `prefetch_late`（注入控制面计划延迟或释放延迟，正是 1.1 / 2.4 的路径）、E3 的转发顺序（注入 3.1 的“Scene 移交早于转发”）都没有自证反例；判定器 5、6 列了反例但没有写“必须报出”的自证步骤。每一条通过条件都应有一个能让它变红的注入。

**9.4【轻】零样本 / 漏选 / 采样窗口**：S:422 对 E2 写了“零迁移、零样本、采样窗口不覆盖交接判失败”，E1 / E3 应同样明示（E1 零 T1、E3 零转发都判失败）。

## 10. 决策与未闭合

**10.1【中】§9 遗漏的玩家可见语义：**
① 合并时施法取消与投射物失效（7.2、7.3）；② 认领第一角丢失、冷却归零（7.2）；③ D13 ② 下合并距离 ≈ 320 m + d_merge、远大于 AOI（6.2）——用户应知道“看不见的人也会让我被合并（并取消施法）”；④ D14 是否含 GM 传送（6.4）；⑤ 认领挂起 / 决定超时的上限（1.6、8.3）；⑥ 冷页争抢的仲裁规则（5.1）若采用“争抢即合并”，也是可见语义（合并更早）。

## 11. 结论

**v6 不能原样批准为第二阶段方向稿。**方向（领导权转移 + 跟随预拷贝 + 所有权前置 + 提前合并 + 转发）与用户“正常路径零停顿、传送一律加载”一致，业界对照也诚实标注了未核实项；但新合同有四处会在**正常路径**导致停顿、卡死或误判僵尸，一处产品语义缺口。批准前最少改以下 6 条：

1. **§4.1 / §4.2**：收尾写回授权扩到 `prepared ∨ committed`，停写时成员页从切点单元集与一切步进域剔除；僵尸判定只对非成员键成立（1.2、2.6）。
2. **§4.2**：源 / 目标化身 bump 事务改写迁移行的 `src_incarnation` / `dst_incarnation`（或守卫改为“该分区行当前化身”）；写明 prepared 提交占一个 seq 且立即排切点，使 T1 的 done 不等 30 s（2.1、2.2、2.4）。
3. **§4.5 + §4.6**：T2 下的顺序合同落到 M4a 移交步骤：seal 等旧 Player 在途体素请求回复（或作为 tail 随 `transfer_cut` 重投）、意图水位随角色行迁移、目标对 prepared 成员的请求排队至翻转（3.1、3.2、3.3）。
4. **§3.3**：冷页争抢仲裁（预取集相交即按提前合并处理，或“更近者持有 + 滞回”）；d_merge 写成随较小岛页数与限速预拷贝带宽的函数并加连锁排队项；d_pre 从“进入预取集”起算（5.1–5.4、1.3、4.3）。
5. **§4.10**：导入对带阻挡成员页核对认领状态，非 pending / 已应用者在导入事务内撤阻挡并处理挂起（8.1、8.2）。
6. **§3.6 + §9**：跟随建立顺序写死为“先登记取 S_reg、再读 PG 至 S_reg”（4.1）；把合并取消施法 / 投射物失效 / 认领第一角 / 冷却归零 / D13 ② 的合并距离 / D14 含 GM 传送列入 §9 由用户拍板（10.1）；D13 推荐改为“S3 验收用 ②，① 并入 S5 一次冻结”（6.3）。

## 总评

v6 把 v5 的四处边缘停顿规则都换成了“先跟随、后一笔翻转、请求排队转发”的无等待形态，方向正确，源码事实陈述经核对全部属实并补齐了两项“未核实”。但新合同在正常路径上有四个可构造的反例：源在 prepared 后被自己的切点或步进判成僵尸自停；化身 bump 后收尾写回永不授权、迁移永不 done；T2 下请求方换进程使转发顺序反转；两分区玩家平行接近时冷页争抢以 30 s 切点周期振荡。另有一处保护区阻挡随页迁入已决定分区后永不撤销。这些都是合同结构缺口而非参数，修订量不大（6 条），修后可批准为方向稿。D13 建议 S3 不绑客户端协议升级；合并附带的施法取消与投射物失效是用户必须知道的可见语义，应进 §9。
